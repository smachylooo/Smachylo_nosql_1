# Spotify: документоорієнтована модель у MongoDB

Навчальний проєкт: завантаження Spotify Tracks Dataset, трансформація через aggregation pipeline, запити та аналіз індексів. **Фактичний запуск на Atlas і результати explain ще потрібно виконати:** наведені нижче пояснення не є звітом про виміряні результати.

## Підготовка

Потрібні Python 3.11–3.13, `mongosh`, доступний кластер MongoDB Atlas і CSV `dataset.csv` із набору [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset). Завантажте CSV вручну з Kaggle або після налаштування облікових даних Kaggle CLI виконайте:

```bash
kaggle datasets download -d maharshipandya/-spotify-tracks-dataset
unzip -- '-spotify-tracks-dataset.zip'
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Вкажіть у `.env` власний `MONGO_URI`; спеціальні символи в імені чи паролі мають бути URL-кодовані. Створіть користувача бази з правами на `spotify` та додайте IP машини, з якої виконується скрипт, до Atlas IP Access List. Не додавайте `.env`, пароль або Kaggle credentials до Git. На M0 перевірте доступний простір: дві колекції разом можуть перевищити ліміт безкоштовного кластера. Команди нижче **видаляють `spotify.tracks_raw` і замінюють `spotify.tracks`**, включно з індексами останньої: використовуйте окремий навчальний кластер або перевірте, що ці колекції не містять потрібних даних.

```bash
python scripts/01_load_data.py
# mongosh не читає .env автоматично; безпечніше ввести URI інтерактивно.
read -rs MONGO_URI; export MONGO_URI
mongosh "$MONGO_URI" --file scripts/02_transform.js
mkdir -p results
mongosh "$MONGO_URI" --quiet --file queries/part2_queries.js > results/part2.txt
mongosh "$MONGO_URI" --quiet --file part3_indexes.js > results/part3_explain.txt
unset MONGO_URI
```

Для `read -rs` вставте URI та натисніть Enter; він не відображається на екрані. Стандартний вивід результатів зберігається у `results/`, яка виключена з Git: перед публікацією перевірте й додайте потрібні знеособлені фрагменти у звіт. Перший скрипт читає CSV частинами та явно розбирає `true`/`false`: приведення непорожнього рядка `"False"` через `bool()` було б помилковим.

## Схема

```json
{
  "track_id": "...", "track_name": "...", "album_name": "...",
  "artists": ["Artist A", "Artist B"], "track_genre": "pop",
  "explicit": false, "popularity": 75, "popularity_tier": "high",
  "duration_ms": 210000, "duration_sec": 210.0,
  "audio_features": {"danceability": 0.8, "energy": 0.8, "loudness": -8.0,
    "speechiness": 0.05, "acousticness": 0.2, "instrumentalness": 0.0,
    "liveness": 0.1, "valence": 0.6, "tempo": 120.0, "key": 5, "mode": 1, "time_signature": 4}
}
```

MongoDB автоматично додає `_id`. `high` означає popularity ≥ 70, `medium` — від 40 до 69, `low` — менше 40. Тривалість у секундах округлена до десятих.

### Чому вкладений об'єкт?

`audio_features` об'єднує характеристики одного змісту та відокремлює їх від назви, виконавців і популярності. Їх зручно отримувати або передавати разом, а за окремим значенням можна звернутися через крапку, наприклад `audio_features.energy`, і індексувати його. Вкладення корисне, коли атрибути належать одному треку і часто читаються разом. Воно менш зручне, якщо група дуже велика, часто змінюється незалежно або має власний життєвий цикл: документ росте, зростає обсяг передавання та оновлень, діють обмеження розміру документа. Для самостійних сутностей може підійти окрема колекція з посиланнями.

### Чому масив виконавців?

Масив представляє кожного учасника окремим значенням, а не фрагментом рядка із роздільником. `find({artists: 'Drake'})` знаходить точний елемент, включно зі спільними треками, без пошуку підрядка; `$all` шукає кількох конкретних виконавців, `$unwind` дозволяє групувати статистику за кожним. Масив також підтримує multikey-індекс. Розбиття і обрізання пробілів виконуються в MongoDB.

## Запити

1. Межі танцювальності й енергії строгі (`> 0.7`), тривалість включає 180000 і 300000 мс.
2. Після `$unwind` підраховуються **унікальні `track_id` для кожного артиста**, оскільки CSV може повторювати трек у різних жанрах. Якщо популярність повторів відрізняється, береться максимальна; це припущення треба враховувати при інтерпретації. Відбираються артисти з ≥ 3 треками і мінімумом ≥ 60; топ впорядковано за середньою популярністю, потім кількістю треків та ім'ям. Середнє округлюється до одного знака.
3. Віконні `$avg` і `$stdDevPop` обчислюють статистику для кожного жанру; відбираються лише значення строго вище `avg + 2 × stdDev`. Повертаються жанри, де знайдено хоча б один такий трек, і масив відповідних треків. Статистика використовує рядки набору даних, включно з повтореннями.
4. Умови `loudness < -10`, `speechiness < 0.1`, `instrumentalness > 0.5`, `explicit: false` застосовуються одночасно.

## Індекси і explain

`part3_indexes.js` записує повний `executionStats` до виводу. Для відтворюваного базового варіанта використано `hint({$natural: 1})`: це примусовий перегляд колекції навіть за наявності інших індексів. Після створення індексів скрипт явно застосовує їх через `hint`, щоб перевірити саме ці варіанти; це **не доводить**, що оптимізатор вибере їх без підказки. Для перевірки автоматичного вибору повторіть відповідний запит без `hint`.

Індекс `(track_genre, popularity, danceability)` спочатку використовує рівність жанру, потім порядок сортування за популярністю, а потім діапазон. Він може уникнути окремого сортування, але через порядок полів може переглядати більше ключів, ніж індекс із діапазоном перед сортуванням. Індекс `(explicit, instrumentalness, speechiness)` починається з рівності, після якої йдуть два діапазони: ефективність другого діапазону залежить від розподілу даних. Порівнюйте на реальних даних.

**Потрібно заповнити після запуску:** для обох запитів вставити сюди з `results/part3_explain.txt` реальні `winningPlan`, `nReturned`, `totalKeysExamined`, `totalDocsExamined`, `executionTimeMillis` до і після; перевірити наявність `COLLSCAN` у базовому плані та `IXSCAN` з назвою відповідного індексу в плані після. Назви та вкладеність стадій залежать від версії MongoDB. Значення часу залежать від кешу й навантаження, тому один запуск не є повноцінним бенчмарком.

### Покривний запит

`find({track_genre: 'pop', popularity: {$gte: 70}})` без проєкції повертає всі поля документа, яких немає в індексі `(track_genre, popularity, audio_features.danceability)`, зокрема `_id`, тому цей запит не є покривним. Проєкція `{_id: 0, track_genre: 1, popularity: 1}` може зробити запит покривним за умови використання цього індексу. Перевірка — фактичний `explain('executionStats')`: `IXSCAN` і `totalDocsExamined: 0` для запиту, що повернув результати, без отримання документів через `FETCH`. Нуль документів при порожньому результаті сам по собі не доводить покриття.

## Локальна перевірка на наданому CSV

Незалежно від MongoDB перевірено умови запитів за допомогою pandas: у CSV 114 000 рядків, після вилучення запису без назви або виконавця — 113 999, жанрів — 114. Умовам вечірки відповідає 7 311 рядків, фонової роботи — 9 324. Поріг середнє плюс два стандартних відхилення перевищують 3 506 рядків у 112 жанрах. Перші виконавці за визначеним у проєкті правилом: Harry Styles (3 унікальні треки, мінімум 89, середнє 92,0), Olivia Rodrigo (5, 86, 87,4), IVE (3, 79, 84,0). Це контрольні результати локальної перевірки, а не результат виконання MongoDB; перед здачею їх потрібно звірити з виводом скриптів Atlas.

### Автоматизований запуск на macOS / Linux

В архів додано `dataset.csv`. Після встановлення Python і `mongosh`, а також заповнення `.env`, можна запустити `./run.sh`. Скрипт запитає підтвердження заміни навчальних колекцій, встановить залежності у `.venv`, виконає етапи та збере вивід у папці `results`. Не публікуйте `.env`; перед поширенням результатів перевірте, чи немає в них конфіденційної інформації.
